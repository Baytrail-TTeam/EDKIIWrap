# Debian Live — próba QEMU, 2026-10-16

Obraz użytkownika: debian-live-13.7.0-amd64-lxqt.iso.
SHA256: 40413e0d337dd104a85441c657d13485e481dcc54227bd56696e6e33457219fb,
zgodny z oficjalnym SHA256SUMS Debian 13.7.0 Live.

Start: OVMF IA32 → BAYTRAIL-USB-IA32-LOWMEM.EFI → nasze EDK2 X64/Shell.
Loader SHA256 cf492ee58130fcf2f631a5c2b533057c849513120bf863ed870d0beee16ec7cb.
QEMU q35/TCG, CPU max, 1 CPU, 1536 MiB. ISO i nośniki USB tylko do odczytu;
brak dostępu do dysków fizycznych i brak instalowania systemu.

Próba ISO/GRUB z 13 października miała nieczytelny framebuffer, bez logu
szeregowego Linux. Zapisane rejestry wskazywały wykonanie w wysokich adresach
jądra; nie dowodzi to zakończenia startu ani wykonania zamierzonych parametrów.
Nie traktować tej próby jako sukcesu, nie ustalono przyczyny uszkodzenia obrazu.

Próba bezpośrednia: wyciągnięte bez zmian live/vmlinuz (linux.efi) i
live/initrd.img z ISO, udostępnione jako osobny USB FAT QEMU tylko do odczytu.
ISO nadal jest USB CD. Sterownik ISO9660 jest ten sam co w teście Windows.
Shell uruchamia fs3:\linux.efi initrd=\initrd.img z parametrami:

```
boot=live components nomodeset earlycon=efifb keep_bootcon ignore_loglevel loglevel=8 console=ttyS0,115200 console=tty0
```

Log potwierdza pełne przekazanie parametrów, EFI v2.7 by Baytrail EDK2 X64,
odczyt ACPI i start Linux 6.12.107+deb13-amd64. Po ok. 2.09 s czasu jądra:

```
No sub-1M memory is available for the trampoline
Kernel panic - not syncing: Real mode trampoline was not allocated
```

Mapa BIOS-e820 przedstawia 0..0x9ffff jako reserved. Pula 4 MiB zaczyna się
od 0x406000 i nie rozwiązuje zapotrzebowania pod 1 MiB. To konkretny błąd
naszego kontraktu pamięci wobec Linux; nie dowód przyczyny niebieskiego ekranu
Windows na tablecie. Pełny start Debian Live, interaktywna konsola, grafika
LXQt i obsługa USB przez Linux nie zostały potwierdzone.

Kod źródłowy jądra: reserve_real_mode() przydziela obszar pod 1 MiB;
init_real_mode() wywołuje panic, jeśli nie ma przydziału:
https://github.com/torvalds/linux/blob/v6.12/arch/x86/realmode/init.c

Dalsza poprawka powinna uzyskać własny przydział pod 1 MiB ze stock IA32
BootServices przed ich zamknięciem, a następnie przekazać go do X64 jako
rzeczywiście posiadaną pamięć. Nie wolno arbitralnie udostępniać całego
0..1 MiB, nadpisywać IVT/BDA/EBDA ani zwalniać obcych rezerwacji.

w tej próbie zmieniono wyłącznie harness, nie firmware ani mapę pamięci.

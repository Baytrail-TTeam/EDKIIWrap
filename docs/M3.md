2026-10-08: zbudowany i uruchomiony w QEMU TCG z **IA32 OVMF**.
Użytkownik potwierdził test na fizycznym tablecie zdjęciem IMG_0428.
[Zapis wyniku i zakres potwierdzenia](MANUAL-TEST-M3-2026-10-08.md).
Bramka do M4 jest spełniona; implementacja M4 pozostaje kolejnym etapem.

## Architektura

Samodzielna aplikacja `BAYTRAIL-M3-IA32.EFI` zawiera X64 SEC adapter oraz
niekompresowany FV (1 MiB) z oficjalnym DXE Core, RuntimeDxe i naszym
sterownikiem diagnostycznym. Nie wymaga dodatkowych plików payloadu.

Collector i transition pochodzą z M1/M2. Przed ExitBootServices IA32
PeCoffLib EDK2 ładuje i relokuje obraz SEC X64. Loader rezerwuje 64 MiB
EfiLoaderData dla DXE, 128 KiB stosu oraz osobne strony dla FV, wejścia,
HANDOFF, mapy i tablic stron. Alokacje pozostają poniżej 4 GiB.
HANDOFF M1/M2 (2312 bajtów) zachowano; rozszerzenie M3 ma 2384 bajty.
Nie ma wywołań stockowego IA32 UEFI po ExitBootServices. Adres jego
SystemTable jest przekazany wyłącznie do porównania z nową tablicą X64.

W X64 adapter korzysta z oficjalnych PayloadEntryHobLib,
PayloadEntryMemoryAllocationLib i `UefiPayloadEntry/LoadDxeCore.c`.
Tworzy HOB-y CPU, zasobów, stosu, framebufferu, ACPI/SMBIOS i FV.
Tylko własna arena trafia do SYSTEM_MEMORY. Wszystkie pozostałe zakresy
stockowej mapy pozostają zarezerwowane lub MMIO; typy ACPI/NVS/runtime
zostają zachowane. Zapobiega to odzyskaniu pamięci stockowego firmware,
framebufferu, przejścia i tabel. Nie jest to pełna polityka pamięci dla OS.

Oficjalny loader DXE ładuje i relokuje DXE Core z FV. Używamy sprawdzonego
stosu i CR3 z M2 zamiast pełnego upstream DxeLoadFunc, który również
obsługuje legacy PIC i nową mapę stron. DXE instaluje własne GDT/TSS/IDT.
Nie dodano inicjalizacji kontrolerów PIC/APIC, PCI, GPIO, USB ani storage.
LocalApicLib jest zależnością biblioteki wyjątków; identyfikator APIC
może być odczytywany w diagnostyce wyjątków. Nie wykonujemy przejęcia AP.

APRIORI uruchamia RuntimeDxe (software CRC32 i runtime architectural
protocol), następnie probe. Probe sprawdza nową SystemTable/BootServices,
CRC32 znanego wektora, AllocatePages/zapis/odczyt/FreePages,
InstallProtocol/LocateProtocol/UninstallProtocol, AllocatePool/FreePool,
GetMemoryMap oraz brak wolnej pamięci poza własną areną. Publikuje
zachowane wskaźniki ACPI i SMBIOS przez X64 Configuration Tables i
sprawdza ich wartości. Nie patchuje tabel i nie wykonuje AML.

Sukces i błędy rysowane są bezpośrednio w odziedziczonym framebufferze.
Po teście CPU wykonuje CLI/HLT; EFI nie wraca do stockowego firmware.
TimerLib jest stubem. Brak pozostałych architectural protocols, BDS,
nowego protokołu GOP, konsoli, USB/FAT i obsługi Windows. Nie należy
traktować tego jako kompletnego środowiska UEFI dla aplikacji/OS.
RuntimeDxe nie oznacza działających sprzętowych runtime services.

## Build i weryfikacja

```sh
./build-m3.sh
python3 scripts/test-m3-qemu.py
```

Wymagania: te same przypięte źródła co M1/M2, LLVM/LLD 23.1.2,
NASM 3.02, Python 3, make i natywny kompilator C/C++ dla BaseTools.
W tej sesji: macOS Apple Silicon, QEMU 11.1.1 z Homebrew.
`LLVM_BIN`/`LLD_BIN` wybierają narzędzia; `QEMU_FIRMWARE` wybiera katalog
z `edk2-i386-code.fd` oraz `edk2-i386-vars.fd`.

Build kompiluje BaseTools, X64 platformę CLANGPDB DEBUG, osadza obrazy,
następnie buduje IA32 EFI. Conf i build outputs są w `build/m3/workspace`.
`SOURCE_DATE_EPOCH=1791331200`, timestamp PE=0, źródła sprawdzane z lock.
Powtarzalność dotyczy użytych wersji narzędzi i tej samej ścieżki checkoutu:
obrazy DEBUG zawierają ścieżki CodeView/PDB. Nie deklarujemy identycznych
bajtów między różnymi systemami i katalogami.

`verify-m3.py` sprawdza architektury/subsystemy, entry, brak importów,
niestripowane relokacje (obrazy PIC mogą mieć pustą directory), FV header
checksum, granice FFS/sekcji, DXE core i oba drivery oraz rzeczywiste
osadzenie SEC/FV/transition w IA32 aplikacji. Wynik i SHA256:
`build/m3/manifest.json`. Logi: `build/m3/{basetools,edk-build,edk-loader-build}.log`.

Test QEMU bootuje właściwą aplikację przez IA32 OVMF, obejmuje EBS,
transition oraz DXE. Sprawdza zielone piksele w trzech wierszach i stan
CS64/HLT=1, zapisuje screenshot i rejestry, kończy tylko własną VM.
Pracuje na osobnym katalogu ESP i kopii zmiennych VM; nie podłącza dysków
hosta ani urządzeń tabletu. Wyniki zapisane w `build/m3/qemu-m3/`.
Zrzut ekranu dodatkowo sprawdzono wzrokowo. Archiwalny raport:
`docs/M3-QEMU-2026-10-08.json`.

## Ręczny test na tablecie

1. Skopiuj **tylko** `build/BAYTRAIL-M3-IA32.EFI` na pendrive FAT32,
   np. do `\EFI\TOOLS\BAYTRAIL-M3-IA32.EFI`.
2. Użyj tej samej ręcznej metody startu jak przy M2 (Boot From File lub
   IA32 EFI Shell). Nie zastępuj działającego M2 ani bootloadera systemu.
   W Shell można wywołać `fs0:\EFI\TOOLS\BAYTRAIL-M3-IA32.EFI`
   po ustaleniu właściwego `fsN:` przez `map -r`.
3. Po collectorze oczekuj kolejno: `M3 X64 ENTRY`, `M3 HOBS READY`,
   `M3 LOADING DXE CORE`, `M3 ENTERING DXE CORE`.
4. Wynik pozytywny to **trzy zielone wiersze**:
   `M3 EDK2 DXE OK`, `BOOT SERVICES TEST OK`, `ACPI SMBIOS TABLES OK`.
   Ekran pozostanie nieruchomy; to zamierzone zatrzymanie CPU.
5. Zrób zdjęcie całego ekranu i podaj nazwę uruchomionego pliku.
   Zanotuj SHA256 kopiowanego EFI, aby powiązać test z buildem.

`PRE-EXIT ERROR` oznacza błąd przed EBS (np. brak ciągłego 64 MiB,
nieobsługiwany PAT/framebuffer lub problem ładowania PE). Loader zwalnia
alokacje i wraca z błędem. Po EBS czerwony komunikat identyfikuje etap;
`M3 EDK2 ASSERT` może pokazać plik/linię/opis. Zatrzymanie na jednym
z białych wierszy lub czarny ekran też są wynikiem negatywnym — sfotografuj
ostatni widoczny stan. QEMU nie weryfikuje SMM, DMA, innych rdzeni ani
zachowania rzeczywistego chipsetu/panelu. W M3 nie rozwiązujemy jeszcze
przejęcia tych mechanizmów; przed bootem OS pozostają osobną pracą.
